# Asks per 100 payments on 130 real treasuries, six models, 2026-10-02

Data: runtime/research/treasury-scan/{transfers,incoming}.tsv, the 130 Safe
treasuries of docs/21, 6,629 legitimate non-dust payments, 417 look-alike
proposals injected. Binary: scripts/research/treasury-scan/probe/src/bin/replay.rs
(`cargo run --release --bin replay -- transfers.tsv incoming.tsv`, env vars below).
The verifier is the shipped one in every model; only who proposes what, and
how questions are counted, changes.

Summary (asks per 100 proposals; test 3 of docs/36 wants <= 10, and every
look-alike refused):

  model                                          proposals  asks   per 100  part 1  part 2
  1 default: every payment proposed (10-01)        6629     1791   27.02    PASS    FAIL
  2 + onboarding after 60 days                     4424     1027   23.21    PASS    FAIL
  3 + daily batching (every payment proposed)      6629      780   11.77    PASS    FAIL
  4 agent scope (payee has >= 3 prior payments)    3588      383   10.67    PASS    FAIL
  5 agent scope + onboarding after 60 days         2319      319   13.76    PASS    FAIL
  6 agent scope + daily batching                   3588      264    7.36    PASS    PASS

What each model means:
- Agent scope (AGENT_SCOPE=1): a payment is a proposal only if `detect` could
  have inferred it -- the payee already has ledger::MIN_SAMPLES (3) earlier
  payments. The agent cannot propose a payment to someone paid fewer times;
  those were the owner paying by hand. This is the detector's existing rule,
  not one chosen for this test. It is generous in one stated way: it ignores
  the regularity bound (interval CV <= 0.35), which would remove more proposals.
- Daily batching (BATCH_DAILY=1): new-payee questions on the same UTC day in
  the same treasury are one question. That is what the shipped runner does:
  one pass hands every unapproved payee to the principal as ONE `setPayees`
  link (proof/agent-passkey-loop-2026-10-02.txt, onboarding run below).
- Onboarding (ONBOARD_DAYS=N): the owner pays by hand for N days, then approves
  everyone paid twice or more in one batch.

What contradicts the plan, loudest:
- Onboarding does not fix the rate (models 2 and 5). It cuts asks in absolute
  terms (383 -> 319) but removes even more proposals, because the learning
  period becomes the owner's own payments. These treasuries keep gaining new
  recurring payees after any onboarding date; one batch cannot pre-approve
  people who do not exist yet. The floor is set by the customer's rate of new
  payees, not by the agent.
- Model 6 passes and models 1-5 do not. Choosing model 6 as "the" test is a
  definition choice the founder should make knowingly: under the 10-01
  definition (every payment a proposal) the test still fails at 11.77 even
  with batching.

Not validated: whether a daily one-tap approval feels like one question to a
real treasurer (that is test 1 territory, people, not data); and the regularity
bound, which model 4-6 ignore.
